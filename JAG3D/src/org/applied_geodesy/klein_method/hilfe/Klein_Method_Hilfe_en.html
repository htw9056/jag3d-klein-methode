0. Step by step: preparing and importing data (1D, 2D, 3D) V0.472

This chapter explains what belongs in which file, how each line looks, which system applies and in which order to click in JAG3D and Klein_Method. The example lines come from the Klein_Method test data (data sets 01 and 05) – you can follow them there one to one. If you keep to the rules, you will not get system errors. (JAG3D menu names are given in English; in the German JAG3D they appear in German.)

The golden rules

  1. One project = one coordinate system. Either all files are delivered in WGS84 (geocentric, or UTM/geographic for 1D points) and Klein_Method converts everything together into the local system – or all files are already local and were created with the same P0. Never convert single files beforehand with your own tool or a different P0: points then end up kilometres off and heights wrong by metres to tens of metres.
  2. One height system. GNSS delivers ellipsoidal heights (ETRS89). Normal heights (NHN, height control points) are converted after the import with Manage quasigeoids … → Convert height control points … (GCG2016). Purely terrestrial networks without GNSS stay in NHN throughout.
  3. Always deliver instrument and target heights (columns 3 and 4 of the total-station files). Target height 0 only if you really sighted the mark itself.
  4. Units: angles in gon, distances and heights in metres (JAG3D: Properties → Formatter preferences). Decimal point, no thousands separators; columns separated by spaces or tabs.
  5. Do not mix point types: either reference points or datum points in one adjustment – otherwise JAG3D stops with “reference points as well as datum points”. All points to be determined are new points.
  6. Point names must be written exactly the same in all files (no spaces in names; “1001” is not “01001”).
  7. Only when the import report shows no red: clean gross errors and start the automatic run.

Procedure step by step (constellation E – the complete case)

For A–D the same steps apply without the files not needed – differences in the next section.

  1. Project → Create new project. Do not change the projection and reduction settings.
  2. Import → Reference points → Reference points 3D (or Datum points → Datum points 3D): GNSS control points, geocentric.
  3. Import → New points → New points 3D: all 3D new points (GNSS and total-station points), geocentric; approximations may be rough.
  4. Import → GNSS baselines → GNSS baselines 3D.
  5. Import → Terrestrial observations: direction sets, slope distances, zenith angles – each with instrument and target height.
  6. Import → … → Reference points 1D or Datum points 1D: height control points with position (UTM or geographic) and NHN height – the same point type as in step 2 (reference or datum points).
  7. Import → New points → New points 1D: turning and setup points (position 0/0 allowed); then Leveling data.
  8. Click the Klein_Method tab. Answer “Convert project into local system (ENh)?” with Convert – all points, baselines and 1D points are converted with one P0, the projection becomes “local ellipsoidal”.
  9. Manage quasigeoids … (in the Klein_Method tab): import GCG2016 once, then Convert height control points … (h = NHN + ζ).
  10. Read the import report (appears automatically when red, otherwise menu Klein_Method → Import report …). Every red item names the cause – fix it first, then continue. For “Position of 1D new points” use the button Take the position ….
  11. Answer the questions on approximate coordinates and merge GNSS sessions with the recommendation.
  12. Look at Klein_Method → Gross-error pre-check, then in the tab Clean gross errors (chapter 7).
  13. Start the automatic run (chapter 6) and export at the end (chapter 11).

Differences for the other constellations

  • A – 1D: import only height control points (name, height), 1D new points and leveling data. No conversion, heights stay NHN, no quasigeoid step. Continue with step 10.
  • B – 2D: 2D reference/new points, direction sets and horizontal distances. Before the import Properties → Projection & reductions: choose UTM or Gauss-Krüger and the desired reductions (local network: “Local Cartesian system”). No conversion by Klein_Method.
  • C – 3D terrestrial: 3D reference/new points local (east, north, NHN), directions, slope distances, zenith angles, levelling if any. Projection “local Cartesian” – without GNSS Klein_Method changes nothing. Note: local Cartesian computes on a plane; for networks above approx. 1 km earth curvature matters (1 km ≈ 8 cm, 3 km ≈ 70 cm) – then better include GNSS or use UTM/Gauss-Krüger.
  • D – 3D GNSS: steps 1–4 and 8, 10–13. Without levelling step 9 is omitted.
  • Files already converted to local (e.g. by your own tool): use them only if all files were created with the same P0. If in doubt, import the WGS84 originals.

1. Typical workflow

  1. Import data as usual in JAG3D (points, terrestrial observations, GNSS baselines).
  2. Open the project – Klein_Method checks in the background whether a conversion to the local system is needed and offers it (chapter 2).
  3. Compute and check approximate coordinates (chapter 3) – above all before averaging (chapter 4).
  4. Click the “Klein_Method” tab – an adjustment runs in the background; GNSS sessions may be merged (chapter 5) and notes on GNSS support are shown (chapter 8).
  5. Clean gross errors if suspected (chapter 7).
  6. “Start Klein_Method” – the automatic run calibrates the accuracies (chapter 6).
  7. Look at the forecast and measurement planning: where is the network weak, what should be remeasured? (chapter 9)
  8. Export coordinates in the desired coordinate and height system (chapter 11).

Workflow assistant V0.480

Tab “Klein_Method” → Control: “Workflow assistant …” · menu Klein_Method → Workflow assistant …

An error in the workflow (wrong coordinate system, NHN and ellipsoidal heights mixed, control point without coordinates) can ruin the entire adjustment. The assistant therefore checks the seven steps from the import to the automatic run and shows a traffic light, the reason and the suitable action for each step:

  • 1 Import and plausibility – import report; control points at 0/0/0 (e.g. name imported twice, GNSS coordinates skipped) are red and can be converted into new points with one button (group “Klein_Method Neupunkte (aus Festpunkten 0/0/0)”, reversible).
  • 2 Coordinate systems – number of geocentric, UTM and local points; mixtures are red.
  • 3 Conversion (only with GNSS) – converted? geocentric leftovers? P0 more than 50 km outside?
  • 4 Height system – GNSS height minus levelling height at common points; mixed NHN is red (chapter 10).
  • 5 Approximate coordinates – observed points without approximation (chapter 3).
  • 6 Repeated measurements – merged or open (chapter 5).
  • 7 Release – green when no step is red and a valid adjustment exists.
No start window: if a step is red, “Start Klein_Method” starts anyway without asking – the red steps are logged (“ABLAUF: Start trotz … roter Schritte”); please check here beforehand. State log: conversions, projections, height conversion, approximations, merging, height from 1D, 0/0/0 conversion and gross error cleanup are stored with a time stamp in the project and shown in the assistant – so it is traceable what happened to the data.

2. Import and conversion to the local system

Menu Klein_Method → Coordinate conversion WGS84 ↔ local (ENh) … · Tab: “Check and convert project …”, “Undo project conversion”, “Move P0 into the network and convert again …”

If coordinates and GNSS baselines are geocentric (ECEF/WGS84), Klein_Method converts the project into a local ellipsoidal system around a reference point P0 (centroid of the new points, false origin 200000 / 400000 / 1000 m). In it, JAG3D computes GNSS and total station together.

Important: In the local system the Z column in JAG3D is not a height but the Cartesian coordinate perpendicular to the tangent plane in P0. With distance it falls below the height by about r²/2R (10 km ≈ 8 m, 30 km ≈ 71 m). This is how JAG3D is designed. Real heights come from the export (chapter 11). See also problem “Z is not a height”.
Only with GNSS baselines V0.468: conversion, moving P0 and any change of projection and reduction (including “local Cartesian → local ellipsoidal” and the principal point) only take place if the project contains active GNSS baselines. Without baselines everything stays as set in JAG3D; a call from the menu states the reason. Undoing an earlier conversion is still possible.

The conversion can be undone; a merge of GNSS sessions is automatically undone first.

Height points (1D) V0.465: they are converted as well – also when imported after the conversion. In the local system Z depends on the position (earth curvature), so every height point needs a position: from its entered position in UTM (with or without zone), Gauss-Krüger (DHDN) or geographic (longitude/latitude in degrees), at most 100 km from P0. Without a usable position (e.g. 0/0) P0 is assumed and the point is named in the prompt – please enter the position (at 2 km from P0 about 0.3 m height error). The height is converted as entered; convert NHN heights afterwards with “Convert height control points …” (quasigeoid) to ellipsoidal. Undoing the conversion also restores the 1D points.

Import report (data plausibility) V0.467

Automatically on the tab click after every new import · Menu Klein_Method → Import report (data plausibility) …

Errors in the imported data otherwise show up in the adjustment as apparent gross errors. The report checks beforehand and shows a traffic light per check: [GREEN] fine, [YELLOW] note, [RED] please clarify before the adjustment. On the tab click the window only appears for red items; the report is always written to the protocol and as the file <time>_Importbericht.txt in the protocol folder.

  • Names: points in observations without coordinates, points without observations, auxiliary/setup points “No_Point”.
  • Reciprocal zenith angles: height difference forward (s·cos z + i − t) plus back should be 0 (tolerance 3 cm + 0.1 mm/m). If many pairs disagree by 1–3 m, instrument or target heights are wrong.
  • Face I/II: index error per target when zenith angles exist in both faces.
  • Instrument and target heights: several instrument heights per station, target height 0 with an instrument height set (see error pattern).
  • Units: a median zenith angle around 85–94 gon suggests degrees instead of gon; distances ≤ 0 or over 5 km; control points with height 0.
  • Systems: geocentric baselines alongside local points; GNSS height minus levelling height above 1 m (NHN and ellipsoidal mixed).
  • 1D points without their own position: 0/0 or several different points at the same place.
  • Position of 1D points versus sight distances V0.471: the path through the levelling (sum of sight distances) is an upper bound for the distance to neighbouring points with their own position (3D points take precedence). If a height control point lies clearly farther away, it was converted with another P0 or in another system – red.

Position of 1D points from the levelling: With the button in the report, 1D new points without their own position receive one: setup points “No_X” take the position of X, all others the mean of their levelling neighbours (starting from the points with a position). The height stays unchanged. To be honest: JAG3D's levelling results do not depend on this position. It is needed for converting the 1D points to the local system (Z depends on the position), for the map and for plausibility checks.

Lock against multiple conversion V0.482

File converter (mode 1) and workflow assistant, step 3

A second conversion or a different P0 distorts the whole network without the numbers showing it. Klein_Method therefore locks on three levels:

  • Files: every converted file gets the header # Klein_Method: lokal (ENh) umgerechnet am …, P0 … (the JAG3D import skips it). A file with this header is not converted again in the same direction, and back only with the same P0. If all points of a file are already in the target system, the conversion is locked as well.
  • Project: Klein_Method only converts geocentric values and backs up every converted row – it is never converted a second time.
  • Local data imported after the conversion (control/connection points, GNSS baselines) that Klein_Method did not convert itself come from a foreign conversion with unknown P0: step 3 of the workflow assistant turns red and the automatic run is locked. Solution: delete these data and re-import them geocentric. New points with such approximations are reported yellow.

Rename points V0.489

Klein menu: “Rename points …”

Renames points and the point names in all observations together – with templates in the drop-down menu, preview, distance check when merging and exact undo. Example: 043.905-A, -B, -C → 043.905.

  • Templates: remove ending “-letter” or “-number/_number”, append ending, remove prefix, replace text, remove leading zeros, pad with zeros to n digits, shift number by n, own regular expression. Search/replace can be adjusted and saved as an own template. Scope: points and observations (normal), observations only, points only; “Only names with” narrows it down.
  • Preview (no change): old and new name, point yes/no, number of observations, traffic light and note. Only ticked rows are executed.
  • Merging: if several points get the same name, each is compared individually with the reference point (existing point of that name, otherwise fixed before new point, higher dimension, with coordinates) – using adjusted coordinates, otherwise approximations. Green: within the tolerance (default horizontal 3 cm, height 5 cm) – same point, merge. Red “eccentric?”: further away – not ticked, keeps its name. Red: fixed points with differing coordinates are never merged. Yellow: coordinates missing – tick only after your own check.
  • The reference point is kept; optionally a new point gets the mean of the approximate coordinates. The other points are deleted, their observations point to the new name. “Undo last renaming” restores everything exactly, including deleted points with the same number. Then adjust again; entry in the state log (“PUNKTE UMBENANNT”).
  • Test (synthetic test network 01): ending appended to 14 points (149 observations) → adjustment error-free, undo exact. T05-B 1 cm next to T05 → green, merged; T05-C 50 cm away → red “eccentric?”, kept; G1-B (fixed point, 20 cm) → red, never merged; X9-A/-B without X9 → X9, undo restores both.

3. Approximate coordinates revised since V0.448

Menu Klein_Method → Compute and check approximate coordinates … and … Undo last adoption of approximate coordinates … · Tab: “Check approximate coordinates now”

Klein_Method computes approximate coordinates from all observations for points without values (0/0) and checks existing values. The results are offered for adoption; a backup allows undoing.

  • GNSS sessions with drift or offset > 0.10 m are reported; if most baselines of a point are rejected, switching them off is offered V0.449.
  • The approximation takes the earth curvature in the local system and the stored position of height points into account V0.448.
Recommendation: always compute approximate coordinates before averaging or adjusting – especially after adding new total-station points to a GNSS network.

5. Repeated measurements (overweight) GNSS since V0.452, all types since V0.477, automatic since V0.478

Tab (approximate coordinates area): “Repeated measurements (overweight):” with one selection per type “Merge / Off”, “Apply now …”, “Undo all …” · Menu Klein_Method → Handle repeated measurements … / Undo handling of repeated measurements …

Directly consecutive measurements from the same station to the same target are not independent: GNSS epochs of one session, several direction sets, distances measured twice, measurement series of a laser tracker. As single observations they weigh about √n times too much and push the other measurements aside. A repetition group consists of consecutive active rows of the same observation group with the same station and target (terrestrial: also the same instrument and target height).

  • Merge: one mean observation per repetition group; the single values are deactivated (not deleted). Accuracy of the mean = that of a single measurement (without √n), but at least the scatter of the group – strongly scattering sessions therefore weigh less. The mean is calibrated normally by the automatic run.
  • Merge + calibrate (default since V0.490): like Merge; means with their own accuracy (strongly scattering or drifting) start with the scatter and are recalibrated by the automatic run from their residuals.
  • Off: all measurements individually as imported.
  • Beforehand every group is checked for a jump (split at the jump) and drift (accuracy = half the drift). Limit = max(3 × single σ, minimum): GNSS 0.10 m, distances 5 mm, levelling 2 mm, directions/zenith angles 5 mgon.
  • Automatic: Klein_Method applies the setting without asking – on tab click, after changing the selection and before starting the automatic run – and then reports what was merged. Undo at any time; after an undo Klein_Method merges again only for new data.
  • After every change a note appears in the protocol and the status line if the automatic run had already run – then restart it if needed (symptom).
  • Reweighting (single σ × √n, V0.477) has been dropped: on a real network (GNSS and total station) points were up to 46 cm off with it, 1–2 cm with merging – the frozen start accuracies (25 mm + 50 ppm) were never calibrated. Reweighted projects are switched automatically on tab click.
  • At the end of every finished automatic run a comparison file “…_Vergleich_Wiederholungen_….txt” is written to the protocol folder with adjustment stage, max logPost, handling per type, share of the total redundancy and the adjusted coordinates.
Result on a real network (5914 baselines in 199 sessions, 6000 total-station observations): after merging, the GNSS points in the total-station block agree with the pure GNSS solution to 1–2 cm; GNSS control points 9 mm on average.

Merge + calibrate (comparison variant) V0.481

Tab: selection per observation type “Merge + calibrate”

Like “Merge”. In addition: means with their own accuracy (strongly scattering or drifting groups) carry an individual σ and do not count towards the variance component of the observation type in JAG3D. In this variant the scatter is only the starting value.   • Protocol: lines “WIEDERHOLUNGSMITTEL …” with F, factor and number of changed means.

Mass baselines (epoch baselines) V0.488

Klein_Method tab, approximate coordinates area: switch “Thin out mass baselines automatically” · workflow assistant step 6

GNSS processing often delivers one baseline per epoch – e.g. 30 min every 1–5 s to 8 SAPOS stations, quickly 100,000 to 300,000 baselines in total. JAG3D cannot compute that on a normal PC, and the epochs are strongly correlated in time (as single observations about root(n) times too heavy). Klein_Method detects such data and thins them out before the first computation.

  • Detection: more than 20,000 GNSS baselines, or from 1,000 baselines on average at least 20 per point pair. The epochs may be in any order and in any number of groups (JAG3D creates a new group per station change when importing with group separation) – they are collected per point pair.
  • Thinning: one robust mean per point pair – median and robust spread per component, epochs deviating by more than 3 spreads (at least 1 mm) are rejected, the mean is formed from the rest; jumps and drift are checked as with “Merge”. The accuracy of the mean is not divided by root(n). The single values stay deactivated in the database – undo at any time (“Undo everything …”).
  • Switch on (default): automatically on the tab click or before every adjustment. Off: with more than 20,000 active baselines the adjustment stays locked (note, step 6 red) until “Thin out now” in the workflow assistant.
  • Only the statistically good epochs remain: JAG3D does not take over fix/float or RMS information when importing baselines. If a whole session is off (wrong fix over 30 min, wrong antenna height), only the adjustment over the other stations or the statistical test shows it.
  • Test (synthetic, 299,300 baselines, 41 point pairs, 2 sessions, correlated noise, 3,066 outliers 5–50 cm): import and tab click without failure, thinning about 1 min → 41 means, all outliers and some edge epochs rejected; afterwards the adjustment is error-free. With the switch off locked, “Thin out now” works; undo restores all 299,300.

Repeated observations / mass baselines

6. Automatic run and calibration

Klein_Method tab: “Start Klein_Method”, “Stop”, “Single step”, “Reset”, “Release lock”

The automatic run calibrates the accuracies of the observations step by step until the limit for the largest logPost value is reached. It runs in passes:

  • Pass 1: group calibration (σa/σb/σc per observation type), then individual calibration.
  • Pass 2: individual fine calibration with fixed group values. It is essential – without it, the results in the test were many times worse.

If an observation reaches the upper limit of the individual measurement uncertainty, it is deactivated as a gross error and the automatic run continues (at most 10 per step, beyond that a lock) V0.454.

At the end a run report and, on request, a calibration certificate are created.

Follow-up: damping and rounding at the threshold V0.497

Automatic run · cascade pass 2 · log “Nachlauf-Daempfung”

In the follow-up of pass 2 the max logPost often oscillated around the threshold instead of reaching it; the state of pass 1 was then taken over.

  • Damping: if the max logPost rises again compared with the previous follow-up iteration, the next correction step of the individual calibration is halved (down to 25 % at most); on improvement it grows back up to 100 %.
  • Rounding: the threshold counts as reached if the max logPost rounded to 3 decimals is not above it (e.g. 2.4504 with threshold 2.450).
  • If pass 2 is better than the backup of pass 1, it is taken over as before.

Limits of the method V1.00 RC1

applies to all adjustment stages

The Klein method makes a network statistically consistent. It does not make the measurements better. These limits should be known:

  • Fixed limit: |logPost| ≤ 2.45 corresponds to p ≤ 0.086. Even in an error-free network about 8 % of the observations lie above it by chance and are down-weighted. Where the a-priori model already fits, single new points can differ by a few millimetres from the classical solution (VKS). This is deliberate: no measured value should remain conspicuous in the result.
  • Lower limits: the group accuracy does not fall below 0.5 mgon or 0.5 mm (electronic) and 0.1 mm (levelling). This prevents the group values from drifting away but limits the adaptation to very precise instruments.
  • No replacement for repetition: errors that affect all observations of a point equally – such as a wrong antenna height with only one GNSS session – are invisible to any adjustment. Independent repeat measurements remain necessary.
  • Check raised accuracies: protocol and calibration certificate show how much each accuracy was raised. Strongly raised groups or many deactivated observations point to measurement problems and should be checked, not just computed away.
  • “not testable”: for connection points marked like this the measurements cannot determine the uncertainty; the result there depends on the input value.
  • Computation in blocks: the method re-adjusts the whole network each time and is not designed for real time.
  • Test basis: tested on synthetic networks with known target coordinates and on practical projects. Comparisons on further real networks with independent control are still pending.

7. Gross errors groups and cross-check since V0.461, pre-check and test statistic since V0.463, cause analysis since V0.464

Tab: “Clean gross errors” · Map: “Max error”, “Clean gross errors”

If an observation deviates linearly after the adjustment by more than the “gross error limit” (default 0.10 m), “Start Klein_Method” is locked until it has been cleaned. The cleanup deactivates the affected observations step by step, with a new adjustment each time.

Why step by step? In the adjustment a gross error “smears” onto neighbouring observations. Removing everything above the limit at once would also lose healthy neighbours.

What is removed together in one step:

  • Cluster at one point (at least 5 and 80 % of the outliers): the strongest of them, from half the largest deviation – usually the point itself is disturbed (set-up, antenna height, mix-up).
  • Scattered outliers V0.461: the worst observation and further ones above the limit that are at least half as large and share no point with one already chosen – at most 10 per step. Neighbours thus stay in and are re-evaluated in the next step.

Cross-check V0.461: at the end the observations that were only taken along (not the worst one of each step) are re-included and recomputed. If they are then below the limit and no other observation stays above it, they remain in; the confirmation window lists them under “Re-included after the cross-check”. Otherwise everything stays as before the cross-check.

Individual cross-check V0.469: If the joint cross-check fails, each observation is re-inserted individually (at most 30, smallest deviation first). It stays if it is then below the limit and no other observation exceeds it. This keeps correct observations that a real gross error (e.g. a point mix-up) merely dragged along.

Safety: if a combined step makes the network undeterminable, Klein_Method undoes it and continues one by one. At most 25 steps per pass – then “Clean gross errors” again.

Pre-check before the adjustment V0.463

Menu Klein_Method → Gross-error pre-check (loop closures, repeated measurements) … · also runs automatically at the start of “Clean gross errors”

Before the adjustment a gross error has not yet smeared. The pre-check changes no data and checks:

  • GNSS loop closures: all triangles of active baselines (median per point pair). Tolerance = gross error limit + 1 ppm of the perimeter. A point pair conspicuous in at least 2 and 60 % of its triangles is suspicious.
  • Individual baselines farther than the limit from the median of their point pair (from 3 baselines per pair).
  • Repeated measurements: distances with equal instrument/reflector heights and levelling forward/back; a spread above the limit is conspicuous.

In the confirmation window such observations are marked “pre-check conspicuous” – a strong indication of a real gross error. The report is in the protocol.

Order and controllability V0.463

The observation with the largest test statistic among those above the limit is removed first – not the one with the largest deviation in metres. The test statistic takes into account how well an observation is controlled; the limit in metres only decides whether it is a candidate at all.

Hardly controlled observations (redundancy share below 5 %) are reported separately: a gross error would not be detectable there – secure them in the field.

Re-inclusion check: besides the observations taken along, individually removed GNSS baselines whose misclosure against the new coordinates is below the limit are also checked.

Robust pre-selection and cause analysis V0.464

Robust pre-selection: if at least 3 observations are above the limit, Klein_Method first removes in one step all those that the pre-check found conspicuous and that are above the limit (at most 50). The pre-check works without an adjustment – a gross error does not smear there. All observations removed this way go into the cross-check at the end.

Cause analysis (GNSS): for each removed baseline the misclosure against the new coordinates is computed (computed without it, hence undistorted). The confirmation window and the protocol then list possible causes:

  • Antenna height: several baselines of one station deviate almost only in height, with the same sign – “Station X: … check the antenna height at X”. A single baseline with a pure height deviation is reported as well.
  • Point mix-up: the vector leads to another existing point (distance at most half the limit, at least 2 cm) – “fits point Y instead of Z”.

The notes are suggestions – the field book decides.

  • Measurement planning: for the weakest points one GNSS session from a reference station is inserted computationally and adjusted. If several points give the same gain, they are named together – choose the most accessible one.
  • Accuracy of the assumed session: “short baseline (5 mm horizontal, 10 mm height)” or “like the previous sessions”. Long baselines to distant stations are often much less accurate (1 ppm is already 30 mm at 30 km).
  • Remeasurement list: deactivated or very uncertain session means.
  • Report “…_Messplanung.txt” in the protocol folder.
Recommendation: call it after the automatic run – only then are the accuracies calibrated.

Dynamic adjustment: lower limit of the fixed points, separate height V0.498

Klein tab: “Dynamic adjustment: lower limit fixed points position/2D/3D (mm)” and “… height control points 1D (mm)” · switch “Height only from height control points (1D)”

A fixed point that cannot be checked with the available measurements used to drop to 0.0001 mm. It was then practically rigid, and the measurements – e.g. GNSS baselines – no longer had any influence on it.

  • Lower limit (every dynamic adjustment): default 1.0 mm for position/2D/3D and 0.3 mm for height control points (1D), adjustable from 0.01 to 50 mm. If a fixed point ends there, the protocol says “FESTPUNKT AN DER UNTERGRENZE … nicht pruefbar”.

If the given heights fit the network, a realistic σ_z results and the height helps to check the point.

  • Free and fixed adjustment are unchanged; in the fixed adjustment the height stays fixed-free with 10 m when “Height only from 1D” is on.

Dynamic adjustment: fixed points end in the band again V0.509

Automatic run in the dynamic adjustment · protocol

With V0.507/V0.508 a fixed point whose T_prio reacts strongly to its σ could count as “interval exhausted” too early and end with T_prio 1.02 instead of 1.00. In addition, the final VKS scaling ran at the end of the dynamic adjustment; if it was kept, the T_prio values of all fixed points shifted afterwards.

  • “Interval exhausted” now applies only to fixed points that hardly react to their σ (|p| < 0.1). If such a point later leaves the tolerance, it is processed again.
  • The dynamic adjustment no longer runs the final VKS scaling – the observations stay unchanged there, and the final T_prio values match the last evaluation in the protocol.

Dynamic adjustment: interval bisection and clear end message V0.507

Automatic run in the dynamic adjustment · protocol and status line at the end of the run

Some fixed points hardly react to their own uncertainty: T_prio changes only slightly over a wide range of σ because it is determined mainly by the rest of the network. Until now σ then moved in very small steps until the stagnation detection ended the run without DONE.

  • If a σ with T_prio above the band and one with T_prio below the band are known for a fixed point, the interval is bisected (geometric mean). Protocol: “Intervallhalbierung (Ziel zwischen … und … mm)”.
  • If the interval is exhausted to 0.1 % and T_prio lies within about 3 % of 1, the point counts as finished – its σ is determined. Protocol: “Intervall ausgeschoepft”.
  • The dynamic adjustment calibrates only the fixed points. If Max-logPost is above the threshold at the end, the status line reports “Control points calibrated. Max-logPost is above the threshold – the observations are calibrated in the fixed adjustment.” This is not an error.

Dynamic adjustment: all individual values of the fixed points filled in V0.506

Point group “movable connection points” (individual σy, σx, σz) · protocol at the end of the run

Until now the individual value of a fixed point stayed empty if the measurements could not check it at all (T_prio ≈ 0) and it had no individual value before – e.g. the z component of a height fixed point. JAG3D then used the group value.

  • At the end of the dynamic adjustment every movable connection point without an individual value gets the effective group value as individual value (2D: y, x; 1D: z; 3D: y, x, z). Nothing changes numerically, but no field stays empty and a later change of the group value does not silently affect these points.
  • Protocol: “EINZELWERT ERGAENZT: … = Gruppenwert – T_prio …”.
  • New note “FESTPUNKT NICHT PRUEFBAR” for points with T_prio ≈ 0, even if they are not at the lower limit.

Lower limit of fixed points only with GNSS, variance factor, final scaling without GNSS V0.503

14. Problems and solutions

Very many zenith angles as gross errors (deviation ≈ 1.3–1.7 m) V0.466

Cause: almost always the target heights (reflector heights) are missing in the import – they are 0 while the instrument height is set. Every zenith angle then aims too low by the target height. Solution: re-import the measurements with target heights and do not accept these zenith angles as gross errors (“Cancel (re-enable everything)”). The pre-check warns about this (in red at the top of the confirmation window); the cause analysis also names individual target or instrument heights. Also check the height system of the height control points – a GNSS-versus-levelling mismatch is shown in red at the top as well.

Averaging reports deviations of about 200 000 mgon

Cause: approximate coordinates are missing, face II is not recognised. Solution: choose “Compute approximations first (recommended)” in the prompt, or beforehand the menu Compute and check approximate coordinates …. The measurements themselves are fine.

Network edge drifts away

Cause: the edge is connected only by the total station (missing GNSS baselines). Solution: Forecast and measurement planning shows the weak spot before the computation and names the point where an additional GNSS session helps most – often one good session anywhere on the affected edge is enough.

Heights in the local system “wrong”

In the local ellipsoidal system Z is the Cartesian coordinate relative to the tangent plane, not a height (see chapter 2). For heights use the export with “Height: ellipsoidal” or “normal height NHN”.

“LOCKED: upper limit of individual measurement uncertainty reached”

More than 10 observations reached the upper limit in one step – this points to a fundamental problem (e.g. wrong starting accuracies, many gross errors). Check the data, then “Release lock”.

Network shape distorted after merging/undoing

The calibration of the automatic run belongs to the previous observations. After merging the repeated measurements or undoing it, restart the automatic run with “Start Klein_Method” (note in protocol and status line).
